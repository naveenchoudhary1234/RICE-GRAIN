# ByProduct2Protein — Build Log

Streamlit app for Hack the Fork 2026 ("Upcycling India's by-products for
alternative proteins"). Diagnosis-first tool, deep dive on rice bran.

## 1. Original app (v1)

- `app.py` — single-page app: dropdown of by-products (guar meal, groundnut
  cake, almond cake, rice bran, pulse residue), limiting compounds +
  treatments, XGBoost protein/bitterness predictor, cost model vs. imported
  pea isolate, "Explain" button calling the Claude API.
- `data/byproducts.json` — protein %, limiting compounds, flavour issue,
  price per kg per by-product. PLACEHOLDER values.
- `data/treatments.json` — compound → candidate treatments with efficacy.
  PLACEHOLDER values.
- `data/literature_data.csv` — synthetic training data for the XGBoost
  model, generated by `scripts/generate_literature_data.py`.
- `README.md` — how to run, data sources, how to replace placeholders.
- `requirements.txt` — streamlit, pandas, numpy, scikit-learn, xgboost,
  plotly, fpdf2, anthropic.

## 2. Upgrade to diagnosis-first workflow (v2)

Rebuilt around rice bran specifically, structured so every number on screen
carries a data-certainty badge and nothing is invented beyond what was
pasted into the evidence files.

### Evidence data files
- `data/rice_bran_evidence.json` — RB01–RB13 table (id, parameter, evidence,
  why_it_matters, intervention_or_measurement, data_status, source_url),
  transcribed verbatim from the pasted brief.
- `data/paper_facts.json` — PF01–PF25 facts from Tan, B.L.; Norhaizan, M.E.;
  Chan, L.C. *Rice Bran: From Waste to Nutritious Food Ingredients*.
  Nutrients 2023, 15, 2503.
- `data/known_gaps.json` — explicit list of what the paper does NOT contain
  (yield, purity, cost, taste-change data, India-specific prices).

### Badge system (`evidence_utils.py`)
Five data-status badges used on every number in the app:
- `published` / `given` — from a cited source
- `measured` — entered by the user from their own lab result
- `assumed` — editable default, not from a lab test
- `synthetic` — generated placeholder data (Demo model tab only)
- `needs_lab_test` — no source yet; shown as "Needs pilot data", never a
  fabricated number

Key functions: `badge()`, `badge_legend()`, `metric_with_badge()`,
`source_expander()`, `paper_fact_expander()`, `range_note()`,
`get_evidence_by_id()`, `load_json()`.

### Diagnosis tab (`tabs/tab_diagnosis.py` + `diagnosis.py`)
5-step flow:
1. Lot details — mill, variety, date, storage history, **bran type**
   (coarse/fine/polish-meal/mixed/unknown), optional lab values (protein,
   moisture, water activity, FFA, peroxide value).
2. Observed defect — rancid/soapy, bitter, astringent, beany, none.
3. Ranked candidate causes — each paired with an evidence ID (RB0x) and a
   named confirming test (`diagnosis.rank_causes`).
4. Route A/B recommendation with pros/cons (`diagnosis.recommend_route`,
   `ROUTES`).
5. Next-best-measurement card — tells the user the single most useful test
   to run next.

Also: FFA screening against published thresholds (PF10: >10% unfit, <5%
desirable, via `diagnosis.ffa_flag`), a Safety & Regulatory panel (RB12
contaminants, RB13 FSSAI status), and an "Explain" button.

### Explain button
Sends Claude only this app's own diagnosis + cost JSON, with a system
prompt restricting it to the provided data, no invented numbers/claims, and
instructions to name the missing test when data is absent. Output lists the
RB-series source IDs referenced. Model string: `claude-3-5-sonnet-20241022`
(placeholder — swap for whatever model ID is actually available).

### Cost tab (`tabs/tab_cost.py`)
Low/base/high cost-per-kg-of-concentrate range, a Plotly yield-sensitivity
chart, and a break-even price vs. imported pea isolate (editable). All
defaults badged `assumed`.

### Evidence tab (`tabs/tab_evidence.py`)
Full RB01–RB13 table and all paper facts (PF01–PF30) with source links.
Overlapping facts are shown as explicit ranges with both badges, never
merged (see below).

### Demo model tab (`tabs/tab_demo_model.py`)
The original XGBoost regressor, moved here behind a red "SYNTHETIC DATA —
NOT FOR DECISIONS" banner, fully decoupled from the Diagnosis tab's logic.

### UI / theme
Tabs layout (`🩺 Diagnosis`, `💰 Cost`, `📚 Evidence`,
`🧪 Demo model (synthetic data)`), badge legend at the top, a permanent
"Limitations" expander at the bottom listing every synthetic/assumed item,
PDF export on the Cost tab.

## 3. IRRI Rice Knowledge Bank addition (v3)

Added PF26–PF30 to `data/paper_facts.json` from the IRRI Rice Knowledge
Bank ("Rice bran" page, CC BY-NC-SA 3.0), each tagged `data_status:
"published"` and `source: "irri"`. A `sources` block in the JSON now maps
`tan2023` and `irri` to their full citations, so facts from different
papers are never conflated.

- PF26: 100 kg paddy → ~5–10 kg bran.
- PF27: bran composition depends on milling process; may contain hull,
  raising ash.
- PF28: modern mills produce coarse bran, fine bran, and polish/meal.
- PF29: rice bran has 10–23% oil; source of vitamins B and E.
- PF30: underutilised in developing countries due to lack of stabilisation.

Where facts overlap (PF02/PF03 vs PF26 on bran yield; PF01 vs PF29 on oil
%), the Evidence tab shows both values side by side as a range, each with
its own source badge, plus a warning: "differs by mill, variety and milling
degree; measure your lot." They are never averaged or merged into one
number (`evidence_utils.range_note`).

Diagnosis tab Step 1 gained a **Bran type** dropdown (coarse bran / fine
bran / polish/meal / mixed / unknown), stored on the lot record
(`diag_results["bran_type"]`), with a caption noting composition differs by
stream and must be measured on the actual lot.

The IRRI citation was added to the Evidence tab's new References section
and to the bottom of the main app page.

## 4. Current known issue

`plotly` is declared in `requirements.txt` but not installed in the active
Python environment, causing `ModuleNotFoundError: No module named 'plotly'`
when running `tabs/tab_cost.py`. Needs `pip install plotly` (or the
`requirements.txt` install) to complete in that environment before the app
will run end-to-end.
